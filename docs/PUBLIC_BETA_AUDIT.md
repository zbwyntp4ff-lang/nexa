## Оставшиеся блокеры публичной беты

### P1 — Распределённая защита от злоупотреблений

Внутренний rate limiter работает в памяти одного процесса. До публичного запуска необходим доверенный CDN/WAF или reverse proxy с распределёнными лимитами для входа, регистрации, сброса пароля, API и ресурсоёмких операций. Заголовки IP должны приниматься только от доверенного proxy. Public-cloud startup now also requires `TRUSTED_EDGE_RATE_LIMIT_ENABLED=true`; this is an operator attestation after external verification, not automatic WAF detection.

### P1 — Хранилище и масштабирование

Часть состояния и очередей остаётся JSON- или in-memory. Текущая конфигурация рассчитана на один экземпляр приложения и один процесс. Startup guard теперь запрещает `WORKFLOWS_ENABLED=true` и worker count, отличный от 1 (через `WEB_CONCURRENCY`, `UVICORN_WORKERS` или `GUNICORN_WORKERS`). Число контейнерных replicas автоматически определить нельзя: оператор должен оставить один экземпляр. До горизонтального масштабирования нужны общая транзакционная БД, распределённые очереди/лимиты и согласованное хранилище.

### P1 — Удаление временных данных после перезапуска

Для вложений добавлен постоянный ownership manifest в каталоге хранения: он содержит только attachment ID, user ID, сгенерированное имя файла и срок жизни; запись выполняется атомарно с ограниченными правами. Удаление аккаунта и TTL-cleanup используют manifest, поэтому могут удалить принадлежащие пользователю файлы и после перезапуска процесса. Метаданные вложений и извлечённый текст по-прежнему находятся в памяти: после рестарта старые вложения не восстанавливаются для чтения, но их файлы остаются адресуемыми для безопасного удаления по владельцу/TTL. Manifest рассчитан на текущий однопроцессный режим; он не заменяет общую транзакционную БД для нескольких workers.

Для видео-файлов также добавлен постоянный ownership manifest с job ID, user ID, именем файла и TTL 7 дней. Доступ к готовому файлу после рестарта проверяется по manifest; удаление аккаунта и периодический TTL-cleanup удаляют файл даже после потери in-memory job. Сам статус/прогресс задачи по-прежнему хранится в памяти и после перезапуска не восстанавливается. До публичной беты необходимо проверить эти сценарии на staging.

### P1 — Staging и production-конфигурация

Проверить на production-like staging:
- регистрацию, подтверждение email, вход/выход и восстановление сессии;
- OAuth Google/GitHub/Apple и device login;
- изоляцию двух разных пользователей;
- вложения, плагины, память, agent tools и видео;
- удаление аккаунта, рестарт и восстановление из резервной копии;
- HTTPS, cookie flags, CORS/CSRF, заголовки proxy и сетевые ограничения.

Перед открытием регистрации должны быть подтверждены:
- `TOKENS_ENFORCE=true`;
- `AUTH_COOKIE_SECURE=true` за HTTPS;
- `AUTH_SKIP_EMAIL_VERIFICATION=false`;
- `AUTH_BOOTSTRAP_FIRST_OWNER=false` и явный список владельцев;
- рабочий SMTP и проверенная доставка писем;
- действительные production AI provider credentials;
- постоянное хранилище, резервное копирование и мониторинг;
- внешний rate limiting.

### P2 — Миграция существующих desktop-данных

Первый запуск переносит legacy-файлы в Electron userData. Старые записи памяти/плагинов без user_id и прежние общие рабочие каталоги нужно проверить на реальной копии пользовательских данных: автоматическое назначение старых unscoped-записей новому владельцу не выполняется во всех форматах.

## Границы аудита

- Проверены критические изменения авторизации, OAuth, cookie/CSRF, SSRF/DNS pinning, sandbox paths, агентных инструментов, plugin secrets, user isolation, account wipe и Electron packaging.
- В PR нет изменений в исходниках billing, Stripe, subscriptions, token charging или balances. Перемещаются только desktop storage paths для локальных данных.
- Не выполнялись платные production-запросы, изменение DNS, production-развёртывание или использование production secrets.
- Не проводился внешний penetration test. CI и ручной code review не заменяют staging и независимый pentest.

## Решение

**PR #5 и follow-up hardening находятся в `main`; автоматические проверки и Docker smoke прошли.** Публичную регистрацию НЕХА пока не открывать до настройки и внешней проверки реального WAF/CDN и прохождения staging-матрицы выше.
